# GGFC V3.25.61 · 출석 한도·기록 성장 강화·최근 5경기 FORM

**2027년 새 출발을 적용하지 않습니다. 현재 기록지의 2026년 경기부터 새 계산으로 재평가합니다.** 시즌이 바뀌어도 BASE는 이어집니다. 원본 경기·선수·사진·SoccerBee 이력은 변경하지 않습니다. 이 문서가 이번 배포본의 적용 기준입니다.

득점·도움·선방 구간·팀별 기록지 기본 가산과 상한·MOM 기본값을 V3.25.60 대비 1.5배로 정했습니다. MOM에는 현재 능력 구간 성장 완화를 새로 적용하므로 높은 점수에서는 실제 증가량이 이전보다 작을 수 있습니다. 점수 범위는 0~99입니다.

출석 가산은 경기 기록 성장과 분리했습니다. 출석 성장 = 명단 출석 가산 × 능력 구간 성장률 × FORM 성장 배율이며 승점 배율은 곱하지 않습니다. 실제 반영량을 축별·연도별로 계산하고 1점을 넘기지 않습니다. 기본 포지션 가중치에서 모든 출석 한도를 채웠을 때 연간 BASE OVR 기여 상한은 PV 0.65 / AL 0.55 / FS 0.85 / GR 0.90입니다. 공식 명단 없이 활동 기록만 있는 경우 출석 보너스는 주지 않습니다.

경기 기록 성장 = 해당 축 기록 기본 가산 × 기존 승점 배율 × 능력 구간 성장률 × FORM 성장 배율. 팀별 기록지 상한은 이 배율들을 곱하기 전 값입니다. 도움·선방 구간은 충족한 최고 구간 하나만 적용합니다. 같은 경기의 중복 행은 중복 보상하지 않습니다.

## FORM의 실제 적용 방식

1. 경기일 5회가 아니라 **실제 출전 경기ID 5개**를 사용합니다. 결석을 0점 경기로 넣지 않습니다.
2. 실제 출전 8경기 이상에서 최근 5경기와 그 직전 최대 20경기(최소 3경기)를 비교합니다. 초기에도 기록 가산은 반영하되 8경기 전 평가는 잠정이며 FORM은 0입니다.
3. 최근 경기 가중치는 최신순 35/25/20/12/8%입니다. 지표의 최근 가중 경기당 평균에 평소 평균 4경기 분량을 섞어 표본을 완화합니다. 평소 평균은 비교 구간의 실제 확인 경기 평균입니다.
4. SHO 흐름 = 득점 변화 40% + 유효슛 변화 60%, PAS 흐름 = 도움 변화 40% + 키패스 변화 60%, 필드 DEF 흐름 = 수비성공 변화입니다. SHO는 골과 유효슛이 함께, PAS는 도움과 키패스가 함께 확인된 경기를 사용합니다.
5. 변화율은 **(보정한 최근 평균 − 평소 평균) / max(평소 평균, 최소 분모)**로 계산하고 −1~+1로 제한합니다. 최소 분모는 득점·도움 0.25, 유효슛·키패스 0.5, 수비성공 1회/경기입니다. 양쪽 모두 0이면 변화율 0입니다.
6. 역할별 SHO/PAS/DEF 비중은 PV 55/30/15%, AL 35/35/30%, FS 15/25/60%입니다. 각 항목은 최근과 평소 구간 모두 80% 이상 기록돼야 하고, 역할 비중 60% 이상이 확인돼야 FORM을 확정합니다. 확인된 축의 역할 비중으로 정규화합니다. 자료 부족은 0·평가 보류이며 빈칸을 0회로 채우지 않습니다.
7. 골키퍼는 선방·실점·실제 수행시간이 함께 확인된 경기의 선방률 차이 70%와 15분당 실점 변화의 역방향 30%로 평가합니다. 두 기간 합계 상대 유효슛 최소 20회, 각 기간 상대 슈팅과 시간이 모두 양수여야 합니다. 팀 실점과 골키퍼 실점 배정 경고가 있는 행은 비율에서 제외합니다.
8. 역할 가중 변화율 50%에서 ±4 OVR에 도달하도록 선형 환산합니다. 최근 MOM은 1회 +0.25 OVR, 최대 +1 OVR를 추가하되 최종 FORM ±4 범위를 넘지 않습니다. 자료 부족을 MOM만으로 해제하지 않습니다.
9. 조회 기준 경기일에 미출전이면 새 FORM을 평가하지 않고 0·보류로 표시합니다. 결석 BASE 감점은 없습니다.

FORM은 6개 축에 각각 더하지 않습니다. CURRENT OVR에 한 번 더하고 기록 성장 배율 0.9~1.1에도 사용합니다. 공개 화면과 모바일 카드에는 단계 숫자 대신 실제 OVR 보정값 또는 ‘평가 보류’를 표시합니다. 기본 순위는 CURRENT 원점수 내림차순이며 같은 원점수는 이름순입니다. 화면의 CURRENT는 반올림 표시하므로 같은 정수라도 내부 순서는 다를 수 있습니다.

## 지속 부진의 BASE 조정

FORM ≤−2가 **실제 출전한 경기일 6회** 이어지면, 이후 최소 4개 출전 경기일 간격으로 하락이 확인된 SHO/PAS/DEF 축을 0.15점씩 조정합니다. 각 축의 변화율도 −25% 이하일 때만 해당합니다. 기본 포지션 가중 OVR 차감은 연간 1점 이내입니다. 결석은 지속 횟수를 늘리지 않고 자료 부족·성과 회복은 연속 판정을 해제합니다. 기존 LONG FORM·회복형 SLUMP의 추가 감점은 꺼서 중복 적용하지 않습니다.

이 구조는 성장·참여·최근 경기력이 함께 반영된 운영 점수입니다. 모든 선수가 반드시 우상향하도록 보장하지 않으며 기록의 기회·역할에 따라 평가 한계가 있습니다. 드문 득점 하나의 유무만으로 최대 하락을 주지 않도록 관련 기록과 표본 완화를 함께 사용합니다.

## SoccerBee와 페어플레이

SoccerBee 환산 기준과 포지션별 OVR 가중치는 유지합니다. 연 2~3회 측정 사이에는 마지막 유효 기준을 유지합니다. 첫 측정은 해당 축의 초기값만 교체하고 경기 성장분을 유지하며, 재측정은 **(새 환산값 − 직전 유효 환산값) × 0.5**를 반영합니다. 측정 미실시만으로 감점하지 않습니다. 처음부터 미측정인 축은 기존 68P를 사용합니다.

개인파울은 페어플레이·팀파울 통계에만 반영합니다. BASE·FORM 감점에 사용하지 않습니다. 팀 승점삭감의 처리 방식과 원본 팀 점수도 유지합니다.

경기기록 도움 칸에 **0**을 적으면 확인된 무도움 경기로 보존하고, 빈칸은 미기록으로 구분합니다. 0을 선수 이름으로 만들지 않으며 Excel 재출력에도 확인된 0이 유지됩니다. 기존 자료의 빈칸을 자동 변환하지 않습니다. 유효슛·키패스·수비성공의 정의는 팀에서 통일해서 기록해야 합니다.

## 현재 기록지 검증

- 현재 선수 66명·294경기의 실제 기록으로 계산했고, 66명 모두 날짜별 증감 합계가 최종 능력치와 일치했습니다.
- 별도 SoccerBee 파일은 제공되지 않아 이 검증에는 측정값이 없습니다. 운영 앱에 이미 보유한 측정은 삭제하지 않으며 적용 결과는 이 검증 수치와 다를 수 있습니다.
- 세부 기록이 한 날짜 두 경기에만 있어, 현재 66명의 FORM은 자료 부족으로 0·평가 보류입니다. 확인되는 득점·도움·MOM·선방·팀별 기록·출석은 새 요율로 성장에 반영됩니다.
- 가상 완전 기록에서는 상승 +4, 부진 −4 FORM과 지속 부진 BASE 조정, 99점 한도, 연간 출석 한도·연도 갱신을 확인했습니다.
- 득점만 드물게 빠지고 유효슛 등 다른 기록이 유지되는 가상 사례의 FORM은 -0.25로, 최대 급락을 만들지 않았습니다. 가정 사례이며 실제 선수의 미래 점수 예측은 아닙니다.
- 개인파울 추가 전후 능력치 동일, 기준일 이후 기록 차단, 최소 8경기 전 FORM 보류, 실제 5경기와 5경기일 구분, 미기록 감점 보류, SoccerBee 분석 합계, 설정 마이그레이션 반복 안전성을 검사했습니다.
- 브라우저와 분석 Worker의 값 일치, 관리자 요율 입력·검증, 모바일 넘침, 실제 분석 메뉴·상세 내역을 확인했습니다.

시작 SHO/PAS가 이전 70에서 60으로 바뀌고 출석 한도와 감점 규칙도 달라지므로, 기록 기본 가산이 1.5배여도 최종 점수가 이전 버전보다 항상 높아지는 것은 아닙니다.

# GGFC V3.25.57 · 관리자 전용 능력치 변동 분석

## 사용 방법

1. 관리자 로그인 → 좌측 ADMIN의 **능력치 변동 분석** 메뉴를 선택합니다.
2. 선수 이름을 입력하고 검색 결과에서 선수를 선택합니다. 이름 입력 중에는 계산하지 않습니다.
3. 필요한 경우 기준일을 선택합니다. 비워 두면 기존 능력치 엔진과 같은 최신 기준을 사용합니다.
4. **선택 선수 분석**을 누릅니다. 기준일부터 처음까지 역산하는 것이 아니라 기존 엔진과 동일하게 시작 능력치부터 해당 기준일까지 기록을 재생합니다.
5. 상단에서 시작 값, 상승·하락 합계, CORE, SLUMP 잔액, BASE 원점수/표시값, FORM, CURRENT OVR을 확인합니다.
6. 날짜별 **이유 보기**에서 경기 성장·MOM·개인파울·결석·사커비 첫 측정/재측정·상하한 보정·이전 LONG FORM/SLUMP·회복형 SLUMP 잔액 영향을 펼칩니다. 적용 전 수치, 원기록, 적용 요율과 배율, 계산 결과를 확인할 수 있습니다.
7. 초기 능력치, 현재/당일 FORM, 현재/당일 SLUMP의 계산 근거도 접힌 상자에서 확인합니다. 능력치/경기·측정 필터와 12건 단위 페이지 이동을 지원합니다.

## 성능 보호 구조

- 회원 화면 진입, 앱 설치 캐시 준비, 일반 메뉴 스와이프 시 분석용 JS/CSS/Worker를 내려받거나 분석하지 않습니다. 관리자 메뉴를 열 때 작은 화면 모듈을, 분석 버튼을 누를 때 계산 모듈을 불러옵니다.
- 별도 Web Worker에서 선택 선수 1명만 계산합니다. 기존 능력치 계산식 자체를 바꾸지 않습니다. SHO/PAS 초기 백분위 등 공통 기준 산정에 필요한 비교 기록도 Worker 안에서만 처리합니다.
- 사진·로고 등 큰 이미지 데이터는 보내지 않습니다. 계산 자료를 100행 단위로 나누어 전달하고 중간에 화면 처리 시간을 확보합니다.
- 모든 날짜의 상세 결과는 Worker에만 보관합니다. 화면에는 요약, 현재 페이지의 날짜 12개, 사용자가 선택한 날짜의 상세만 전달합니다.
- 새 분석, 취소, 메뉴 이동, 로그아웃, 현재 화면 데이터 재렌더 시 이전 작업을 종료합니다. 첫 분석은 60초 제한이며, Worker를 지원하지 않으면 화면 스레드로 대신 계산하지 않고 안내합니다.
- 결과를 Firebase나 공유 DB, 로컬 저장소에 추가로 저장하지 않습니다. Worker 계산이 끝난 뒤에는 페이지·상세 요청에만 응답합니다.
- 기기 성능과 DB 크기에 따른 분석 대기시간 자체를 0으로 보장하지는 않습니다. 일반 화면에 새 분석 비용이 붙지 않도록 분리한 방식입니다.

## 계산의 의미

- 현재 DB와 현재 관리자 설정을 재계산한 설명입니다. 과거에 다른 설정을 사용했을 당시의 확정 감사 로그는 아닙니다.
- 기존 핵심 함수와 SLUMP 엔진을 빌드 시 추출하고 읽기 전용 추적 코드를 추가합니다. 서로 다른 계산식을 별도로 유지하지 않습니다.
- 날짜마다 `이전 BASE + 항목별 증감 = 이후 BASE`, 전체 기간의 `시작 값 + 누적 증감 = 최종 BASE`를 검증합니다. 검증 실패 시 수치를 표시하지 않습니다.
- 이전 영구 감점, 회복 가능한 SLUMP 잔액, FORM의 CURRENT 보정을 구분합니다. FORM은 6개 BASE 능력치에 직접 더하는 값이 아닙니다.
- 기준일 이전 기록이 없으면 초기값을 확인할 수 있습니다. 능력치 시스템 OFF일 때는 참고 계산임을 안내합니다.
- 공통 원자료 경고는 경기 50건·팀 기록 연결 50건까지만 표시합니다. 누락 기록을 임의로 채우지 않습니다.

# GGFC V3.25.51 · 공통 선수 사진 관리

## 사용 방법

1. 관리자 로그인 후 좌측 메뉴 **선수 사진 관리**를 선택합니다.
2. 선수 이름을 검색하고 선수 타일을 선택합니다. 선수명단·팀스쿼드·역대기록·역대 운영진의 이름을 통합 표시합니다.
3. **사진 선택**에서 PNG / JPG / WebP를 고릅니다. 미리보기 후 **사진 저장**을 누릅니다.
4. 화면 하단에 **공유 저장 완료**가 표시되면 다른 회원도 같은 사진을 사용합니다.
5. 사진을 바꾸려면 새 파일을 선택하고 저장합니다. **업로드 사진 삭제 → 사진 저장**은 기존 엑셀 사진으로 복귀합니다. 저장 전에는 **변경 취소**가 가능합니다.

## 적용 범위와 우선순위

**관리자 업로드 사진 → 각 화면의 기존 엑셀 사진 → 이름/기본 표시** 순서입니다.

- 일반/배경제거 URL로 나뉘던 선수 사진을 업로드 사진 하나로 통일합니다.
- 선수카드, Team Squad 등록 카드와 감독·코치, Player Stats / Ratings, Weekly Best 5, Player Analysis / Chemistry, Team Maker, All-Time Records, 역대 운영진, 사진이 포함되는 이미지 저장에 적용합니다.
- 현재 선수명단에 없는 역대 회원·운영진도 사진을 등록할 수 있습니다. 사진 등록으로 선수 능력치나 경기기록을 새로 만들지 않습니다.
- 업로드 사진은 연도별 사진 이력과 별개인 현재 공통 사진입니다. 과거 시즌을 조회해도 현재 업로드 사진이 표시됩니다.
- 업로드하지 않은 선수의 기존 URL은 계속 사용합니다. 업로드 사진을 지워도 원본 엑셀 URL은 남아 있습니다.
- 동일 이름의 시즌별 행은 같은 선수로 취급합니다. 동명이인은 기존 DB처럼 이름을 구분해서 등록해야 합니다. 선수명 변경은 새로운 이름으로 사진을 등록하세요. 기존 업로드 항목은 직접 삭제할 때까지 유지합니다.

## 저장 구조

- 별도의 유료 저장소나 Firebase Storage 설정 없이 기존 Firebase Realtime Database 공유 기능과 관리자 인증을 사용합니다.
- `DB.settings.playerPhotos = { version: 1, entries: { 선수키: { name, image, width, height, updatedAt } } }`
- 이미지 파일은 브라우저에서 압축한 후 공유 설정에 저장됩니다. PC 한 대의 로컬 경로만 저장하는 방식이 아닙니다.
- 원본 `roster.photo`, `roster.photoCutout`는 수정하지 않고 표시할 때 업로드 사진을 우선 선택합니다. 경기·능력치 계산 로직은 변경하지 않았습니다.
- 선수별 최대 640px, 저장 문자열 96 KiB 이하로 최적화합니다. 원본은 15 MiB 이하 PNG/JPG/WebP, 최대 4천만 화소입니다. 큰 사진은 비율을 유지해 더 작게 압축될 수 있습니다.
- PNG/WebP의 투명 배경을 유지합니다. 배경을 자동으로 지우지는 않습니다. 배경 제거 사진은 투명 PNG/WebP로 준비하세요. HEIC/GIF/SVG 업로드는 지원하지 않습니다.
- 업로드 사진 전체는 약 4 MiB 이내로 제한하며 메뉴에 용량을 표시합니다. 기존 전체 공유 DB 8 MiB 한도도 저장 전에 검사합니다. 이미지 저장량에 따라 첫 데이터 수신량은 증가하므로 필요한 선수 사진만 등록하세요.
- 엑셀 재등록은 업로드 사진을 유지합니다. **JSON 백업/복원에는 사진이 포함**됩니다. 엑셀 내보내기에는 기존 사진 URL이 유지되므로 사진을 보관할 때는 JSON 백업을 사용하세요.
- 기존처럼 전체 JSON 복원·샘플 적용·전체 기록 삭제는 DB 전체에 적용됩니다. 사진도 해당 백업/새 DB 상태를 따릅니다.
- 저장 전 사진 편집은 미저장 변경으로 보호하며, 서버 충돌·연결 해제 시 저장을 차단합니다. 저장 완료를 확인한 뒤 창을 닫으세요.

- 개별 PI도 기준 이하인 SHO/PAS/DEF만 감점합니다. GR은 DEF만 대상입니다. PI 70~75: −0.20, 60 이상 70 미만: −0.35, 60 미만: −0.50 능력치 점수. 연간(1~12월) 신규 감점 한도는 1.5 OVR입니다.

## 반영 사항

1. **Team Squad 이미지 저장**: 저장 범위·선수 명단 포함·저장 버튼을 모두 관리자 모드에서만 표시합니다. 함수 직접 호출도 관리자 인증을 확인합니다. 기존 관리자 PNG 저장 기능은 유지합니다.
2. **Player Stats**: 하단 `스페셜 기록 (우승 · 연혁)` 상자와 해당 화면의 렌더링/검색 연결을 제거했습니다. DB.specials, 엑셀 입출력, 선수카드 업적·우승 계산은 삭제하지 않았습니다.
3. **Interleague Stats**: 상단·사이드바 및 모바일 스와이프에 새 메뉴를 추가했습니다. 기본 공개 상태이며 메뉴 공개 관리에서 공개 여부·이름·순서·첫 화면을 설정할 수 있습니다. 이미 저장된 메뉴 순서가 있으면 기존 순서를 보존하며 새 메뉴를 뒤에 추가합니다.

### 리그 간 전적

- 슈퍼리그와 챌린지리그의 경기 수, 승·무·패, 승률, 득점·실점
- 시즌별 리그 비교, 팀별 인터리그 전적, 경기별 결과
- 전체 시즌 또는 시즌별 / 상·하반기별 조회
- 팀별 인터리그 표에서 팀을 선택하면 해당 팀의 인터리그 역대 전적으로 이동

### 팀별 역대 전적

- 팀 선택 → 통산 경기 수, 승·무·패, 승률, 득실점
- 상대팀별 전적과 실제 경기 이력
- 전체 대회 / 인터리그만 / 개별 대회 선택
- 새 메뉴 내부의 조회 조건을 적용하며 사이드바의 다른 메뉴용 대회 선택과는 독립적
- 기본은 전체 기간이며, 필터를 선택하면 해당 기간의 전적 표시
- 표는 중앙 정렬, 모바일에서 표 영역만 가로 스크롤, 경기 이력은 30개씩 페이지로 표시

## 집계 기준

- 승률 = 승 / (승 + 무 + 패) × 100, 소수점 한 자리. 무승부를 분모에 포함합니다. 경기가 없으면 `—`입니다.
- 기존 검증 경기 목록을 사용합니다. 같은 내용의 중복 경기는 한 번만, 충돌한 중복 경기는 기존 검증 로직에 따라 제외합니다.
- 인터리그는 정규리그/슈퍼/챌린지/인터리그 등 **리그 계열 대회 중 경기일 당시 A팀과 B팀의 맞대결**입니다. 대회명만으로 판정하지 않습니다.
- 각 경기일 이전의 최신 팀스쿼드 그룹을 적용하므로 팀의 승격·강등/리그 이동 이전 기록을 현재 소속으로 소급하지 않습니다.
- 팀스쿼드가 없는 구양식은 기존 경기 그룹을 사용합니다. 둘 다 없으면 리그 간 비교에서 제외하고 집계 기준의 확인 목록에 표시합니다. 팀별 전체 대회 기록에는 점수와 팀이 유효하면 포함합니다.
- 같은 리그끼리 대전인데 대회명이 인터리그로 잘못 표기된 경우 리그 간 비교에서 제외합니다.
- FA컵·챔스 등의 교차 리그 대진은 리그 간 비교에서 제외하며 팀별 전체/개별 대회에서 확인합니다.
- 승패·몰수 결과는 기존 `matchResult` 판정을 재사용합니다. 득실점은 기록된 점수를 사용합니다. 승점삭감은 승패·승률을 변경하지 않습니다.
- 빈 점수, 음수/소수 등 잘못된 점수, 날짜 오류, 미래 예정 경기, 상대팀 누락/동일팀 대진을 새 메뉴 통계에서 제외합니다. 기록된 0:0은 유효한 무승부로 취급합니다.
- 역대 전적은 **등록된 경기기록의 범위**입니다. 역대기록 시트의 개인 통합득점·참석수만으로 과거 팀별 대진을 복원하지 않습니다.
- 경기·능력치·FORM·SoccerBee 등 기존 계산식과 DB 구조는 변경하지 않았습니다.

# GGFC V3.25.38 · 전체 메뉴 모바일 스와이프 개선

## 개선 내용

1. **긴 화면의 이동 범위 제한**: 실제 화면 DOM을 복제하지 않고 화면 크기의 클리핑 컨테이너 안에 잠시 배치합니다. 스와이프할 때 긴 표·카드 목록 전체 높이만큼 큰 이동 레이어를 만들지 않도록 했습니다. 전환·취소 후 원래 DOM 위치, 스타일, 스크롤 및 접근성 상태를 복원합니다.

3. **불필요한 배경 렌더링 제거**: 인접 메뉴를 idle callback에서 자동 계산하던 작업을 전부 제거했습니다. 가벼운 메뉴도 DB가 커지면 UI 스레드를 점유할 수 있기 때문입니다.
4. **메뉴 DOM 재구성 최소화**: 순서·이름·공개 여부·관리자 상태·브랜드가 그대로이면 상단 메뉴를 재생성하지 않습니다. 같은 메뉴 이동 요청 안에서 중복 실행하던 메뉴 선택 처리를 줄였습니다. 설정이 바뀌면 즉시 반영합니다.

## 동작

- 화면의 일반 영역을 좌우로 밀면 현재 화면과 옆 메뉴의 실제 화면이 손가락 위치를 따라 함께 움직입니다.

- 관리자 메뉴 순서와 공개 여부를 따릅니다. 비공개 메뉴를 건너뜁니다.

## 기존 관리자 설정

관리자 → 메뉴 공개 관리 → 모바일 메뉴 스와이프의 사용 여부와 낮음/보통/높음 민감도를 그대로 사용합니다. 새 설정 저장이나 엑셀 변경은 필요하지 않습니다.

- 거리 기준: 보통 = 화면 너비의 18%, 최소 60px/최대 100px. 낮음 1.4배, 높음 0.7배.
- 빠른 넘기기: 최소 32px 이상 이동하고, 최근 이동 속도가 보통 기준 0.55px/ms를 넘으며 손을 놓는 방향과 일치할 때. 낮음·높음은 속도 기준에도 같은 배율을 적용합니다.

# GGFC V3.25.35 · 관리자 화면 조절 · Team Squad 이미지 저장

## 1. 모바일 스와이프

관리자 로그인 → 메뉴 공개 관리 → 모바일 메뉴 스와이프에서 사용 여부와 민감도를 선택하고, 페이지 아래 설정 저장을 누르세요.

- 사용 여부: 켜기/끄기. 기본값은 켜기입니다.
- 민감도: 낮음/보통/높음. 기본값은 보통이며 이전 기준을 유지합니다.
- 보통의 최소 수평 이동거리 = 화면 너비의 18%, 최소 60px·최대 100px.
- 낮음은 보통 거리의 1.4배, 높음은 0.7배입니다. 예를 들어 390px 화면은 약 98/70/49px입니다.
- 기존 1.2초 제한, 세로 스크롤 판별, 가장자리 24px 보호 및 입력칸·버튼·그래프·가로 스크롤 표 제외 규칙을 유지합니다.
- 관리자 저장 후 회원에게도 적용됩니다. 설정을 편집하거나 이미지를 만드는 동안 스와이프 전환을 막습니다.

## 2. 감독·코치 사진 조절

관리자 로그인 → Team Squad → Team Squad 디자인 설정 · 관리자를 펼치세요.

- 사진 조정 대상에서 전체 팀 공통 또는 개별 팀을 선택합니다.
- 감독과 코치 각각 크기 60~150%, 좌우·상하 -30~+30px를 조절합니다.
- 100%는 기준 크기이고, +값은 오른쪽/아래로 이동합니다. 화면이 좁으면 사진을 가용 공간에 맞춰 비율대로 축소합니다.
- 공통 설정은 개별 설정이 없는 팀에 적용됩니다. 개별 팀을 처음 조절하면 당시 공통값을 복사하여 그 팀만의 설정을 만듭니다.
- '이 팀 사진을 공통 설정으로'는 해당 팀의 개별 설정을 해제합니다.
- 전체 공통 대상의 '전체 디자인 기본값'은 사진·배경 로고·테두리와 모든 팀별 조절값을 초기화하는 미리보기입니다. 저장 전에는 서버 기록이 바뀌지 않습니다.
- 변경은 아래 팀 상자에 즉시 미리 보입니다. 디자인 설정 저장으로 공유하며, 변경 취소는 저장된 값으로 돌아갑니다.
- 사진 원본은 기존 선수명단의 배경삭제 URL 선택 규칙을 유지합니다.

## 3. 배경 로고

같은 디자인 설정에서 전체 팀 공통으로 조절합니다.

| 배치 너비 | 상자 너비의 30~90% | 52% |

Team Squad → 이미지 저장 범위 → 전체 팀 또는 개별 팀 선택 → 필요하면 선수 명단 포함 → 공유 이미지 저장.

# GGFC V3.25.32 · Loading Optimization

V3.25.31을 기준으로 로딩·캐시 계층만 개선했습니다. 선수 능력치·성장·FORM·SLUMP, 승점·순위, 베스트커플·DUO, 카드·메뉴·출력 디자인의 계산 및 기능 코드는 변경하지 않았습니다.

## 달라진 로딩 순서

1. 로컬 프로그램을 준비하고, 이전에 받은 동일 Firebase 프로젝트의 기록이 있으면 즉시 표시합니다.
2. ‘최근 기록 표시 중 · 최신 데이터 확인 중…’ 상태에서 Firebase 라이브러리와 최신 기록을 백그라운드로 불러옵니다.
3. 최신 기록 수신 후 기존 실시간 동기화 방식으로 화면을 갱신합니다.
4. 캐시가 없는 첫 방문은 정상적인 서버 수신을 기다립니다. 캐시 손상·저장공간 부족 시에도 서버 읽기는 계속 진행합니다.

기존 12초 타이머는 캐시를 표시하기 위한 대기 시간이 아니라 연결 지연 안내로만 사용합니다. Firebase SDK 버전은 기존 10.12.2, DB 경로는 기존 `ggfc/v3`입니다. DB 구조나 보안 규칙을 변경하지 않습니다.

## 적용한 최적화

| 항목 | 적용 내용 |
|---|---|
| 기록 캐시 | 기존 프로젝트별 localStorage 캐시를 최초 표시부터 사용하고 서버에서 갱신합니다. 관리자 저장이 성공한 최신 값도 캐시에 반영합니다. |
| Firebase 로딩 | SDK 3개가 HTML 파싱과 캐시 기록 표시를 막지 않도록 백그라운드에서 기존 순서대로 불러옵니다. |
| 이미지 저장 | HTML의 html2canvas 선행 다운로드를 제거했습니다. 기존 이미지 저장 시점의 Lazy Loader를 그대로 사용합니다. |
| 정적 파일 캐시 | Service Worker가 HTML·CSS·JS·로컬 SVG·폰트 29개를 검증해 보관합니다. 재접속 시 이 파일들을 재사용합니다. |
| 파일별 버전 | 변경하지 않은 파일의 `?v=3.25.31`은 유지합니다. 동기화·캐시 로더만 `?v=3.25.32`입니다. |
| 배포 안정성 | SHA-256이 맞는 전체 정적 파일이 준비된 경우에만 새 캐시가 설치됩니다. 업데이트 중 기존 캐시와 해시가 동일한 파일은 다운로드 없이 재사용합니다. |

Firebase 데이터·인증 요청, 외부 선수 사진, 외부 라이브러리는 Service Worker 캐시 대상에 넣지 않습니다. `firebase-config.js`는 서버 우선 확인, 실패 시 이전에 저장된 설정을 사용합니다. 설정은 일반 정적 파일과 다르게 독립 갱신됩니다.

첫 방문에는 캐시를 만드는 다운로드가 발생합니다. 재방문 때 효과가 크며, 기기 성능·네트워크·DB 크기에 따라 속도는 달라집니다. 캐시가 지워진 기기는 다시 최초 접속 과정을 거칩니다. 이미지 저장용 외부 라이브러리, 로그인 및 최신 기록 수신에는 인터넷 연결이 필요합니다.

기능 JS 분할 Lazy Loading과 Firebase 화면별 분리 수신은 적용하지 않았습니다. 의존성과 계산 흐름을 그대로 유지하기 위한 범위 선택입니다.

## 관리자 저장 보호

- 캐시를 표시해도 서버 수신 완료 상태로 취급하지 않습니다.
- 인증·최신 서버 수신·연결 상태가 확인되기 전에는 편집과 저장을 허용하지 않습니다.
- 기존 revision 트랜잭션과 충돌 검사를 유지합니다. 편집 중 다른 관리자의 변경이 오면 미저장 내용을 덮어쓰지 않습니다.
- 서버 기록이 비어 있으면 오래된 캐시도 비웁니다. 캐시를 서버에 자동 업로드하지 않습니다.
- 새 프로그램이 준비되어도 열린 화면을 강제로 새로고침하지 않습니다. 저장을 마치고 GGFC 탭을 모두 닫았다가 다시 열면 준비된 업데이트가 적용됩니다.

Service Worker를 사용할 수 없는 환경에서도 기존 HTTP 로딩 방식으로 실행합니다. 캐시는 HTTPS(GitHub Pages) 또는 localhost에서 동작하며, ZIP을 풀어 `file://`로 여는 방식에서는 활성화되지 않습니다.

## 4. 출전 경기와 R의 구분

| 단위 | 의미 |
|---|---|
| 출전 1경기 | 검증된 대진 한 경기에서 선수1~15 명단 또는 허용된 양수 활동 기록으로 확인된 참여 |
| 1R | 기존 FORM과 같은 선수의 경기일. 같은 날 4경기 출전하면 표본은 4경기, 지속 판정은 1R |
| Recent | 해당 시점까지 최근 출전 10경기 |
| Baseline | Recent 바로 이전 최대 20경기, 최소 10경기 필요 |

동일 날짜 내 경기는 경기번호·라운드·고유 경기 키 순으로 정렬합니다. 같은 날짜의 모든 기록을 모은 뒤 R 판정을 한 번 수행합니다. 충돌 경기·중복 대진은 기존 검증 목록으로 처리합니다. 몰수 경기는 실제 출전 표본에서 제외합니다. 양 팀 참여가 충돌한 선수도 제외합니다.

공식 출석 명단이 빠져도 골·도움·MOM·유효슛·키패스·수비성공·선방의 양수 기록과 연결이 확인되면 분석용 참여 근거로 사용할 수 있습니다. **이 기능이 공식 참석수나 출석 가산을 새로 부여하지는 않습니다.**

결석한 날에는 최근 출전 창에 가짜 0기록을 넣지 않습니다. 그날은 신규 감점하지 않고 `PAUSED`로 표시합니다. 지속/회복 연속 횟수는 끊습니다. 이후 새 실제 출전 기록으로 다시 연속 판정합니다.

## 5. 경기당 기록과 100점 기준

```text
경기당 기록 = 해당 비교기간 기록 합계 / 해당 비교기간 실제 출전 경기 수
Performance = 최근 경기당 기록 / 과거 경기당 기록 × 100
최종 지표 = 50~120 범위로 제한
```

| 조건 | 지표 |
|---|---:|
| 과거 0, 최근 0 | 100 |
| 과거 0, 최근 양수 | 120 |
| 과거 양수, 최근 0 | 50 |
| 과거 0.50골/경기, 최근 0.35골/경기 | 70 |
| 자료 누락 또는 확인 불가 | N/A · 제외 |

필드 계산에는 분당·15분당·시간 보정이 없습니다. 드리블 성공·턴오버·수비블록은 DB에 있어도 새 엔진에서 읽지 않습니다.

## 6. 누락 자료와 부분 데이터

미기록을 0으로 바꾸지 않습니다. **최근 또는 과거 구간에 한 경기라도 값이 미확인인 지표는 해당 지표 전체를 비교에서 제외**합니다. 기록된 경기만으로 분모를 줄여 비교하지 않습니다. 남은 지표 가중치를 재분배하고 `부분 데이터 기반`으로 표시합니다.

- 골: 해당 팀의 득점자 합계가 팀 득점과 맞는 경기만 사용합니다. 합계가 맞으면 해당 선수의 득점 명단 부재는 0골로 봅니다.
- 도움: 해당 경기·팀에 도움 기록이 있거나 팀 득점이 0인 경우만 0을 판단할 수 있습니다. 빈 도움 칸과 실제 무도움은 기존 DB에서 구별할 수 없어 그 외는 N/A로 처리합니다.
- 유효슛·키패스·수비성공: 연결된 팀별 기록지의 명시 숫자만 사용합니다. 입력 `0`은 유효, 빈칸은 N/A입니다.
- MOM: 확인된 수상 횟수만 보너스로 사용합니다. 미수상을 감점 근거로 삼지 않습니다.
- 포지션 불명 또는 모든 사용 지표가 N/A이면 `INSUFFICIENT DATA`, 감소 없음입니다.

예: 과거 유효슛이 누락됐지만 골 기록이 모두 확인되면 SHOOTING은 골 100%로 임시 계산합니다. 수비성공이 누락됐으면 DEF 감소를 만들지 않습니다.

## 7. 축·포지션별 가중치

| Index | 구성 |
|---|---|
| SHOOTING | 골 Performance 60% + 유효슛 Performance 40% |
| PASSING | 도움 Performance 50% + 키패스 Performance 50% |
| DEFENSIVE | 수비성공 Performance 100% |

| 포지션 | SHOOTING | PASSING | DEFENSIVE |
|---|---:|---:|---:|
| PV / PIVO | 55% | 30% | 15% |
| AL / ALA | 35% | 35% | 30% |
| FS / FIXO | 15% | 25% | 60% |

선수명단의 해당 연도 포지션을 기존 OVR 시스템과 동일하게 읽습니다. 종합 PI에는 Recent의 MOM 1회당 +3, 최대 +6을 더하고 120을 상한으로 합니다. MOM은 개별 Index를 올리지 않습니다. 위 가중치는 **Performance 가중치**이며 기존 능력치 OVR 가중치와 다릅니다.

## 8. 상태·확정·감소량

| 종합 PI | 관찰 상태 |
|---|---|
| 85 이상 | NORMAL |
| 75 초과 ~ 85 미만 | WATCH |
| 70 이상 ~ 75 이하 | SLUMP |
| 60 이상 ~ 70 미만 | SEVERE SLUMP |
| 60 미만 | CRITICAL SLUMP |

소수점에 빈 구간이 생기지 않도록 연속 범위로 판정합니다. 위 관찰 상태는 감점 확정을 의미하지 않습니다.

**CONFIRMED SLUMP 기본 조건 — 모두 충족:**

1. 현재 FORM ≤ −2.
2. 종합 PI ≤ 75.
3. Recent 실제 출전 10경기와 Baseline 최소 10경기 확보.
4. 같은 조건이 실제 출전한 경기일에서 4R 연속 지속.
5. 적용 시작일 이후. 지속 횟수도 시작일 이후부터 누적.

처음 확정한 R에서 한 번 적용하고, 이후 최소 4R 간격을 둡니다. 조건이 끊어지면 다시 4R 연속을 확인합니다. 각 날짜는 한 번만 판정합니다.

| 해당 개별 Index | 해당 축의 1회 감소 |
|---|---:|
| 70 이상 ~ 75 이하 | −0.20 능력치 |
| 60 이상 ~ 70 미만 | −0.35 능력치 |
| 60 미만 | −0.50 능력치 |
| 기준 초과 또는 N/A | 0 |

Overall이 낮아도 개별 Index가 정상인 축은 감소하지 않습니다. `SHOOTING→SHO`, `PASSING→PAS`, `DEFENSIVE→DEF`; **PAC·DRI·PHY는 신규 SLUMP 감소 대상이 아닙니다.** 기존 SoccerBee 변화나 기존 결석 처리가 이 세 축에 미치는 효과는 유지됩니다.

예: 확정 상태에서 SHO Index=65, PAS=82, DEF=91이면 SHO만 −0.35입니다. PV의 기존 SHO OVR 가중치가 0.25라면 직접 OVR 영향은 `0.35×0.25=0.0875`입니다. −0.35 OVR를 직접 빼는 것이 아닙니다.

## 9. GK 전용 판정

```text
SAVE % = 합산 선방 / (합산 선방 + 합산 실점) × 100
GA / 15 = 합산 실점 / 합산 GK 시간 × 15
GK PI = SAVE% Performance × 70% + GA/15 Performance × 30%
```

SAVE%는 최근/과거 비율, GA/15는 **과거/최근 비율**로 평가합니다. 각 비교 지표는 50~120 범위입니다. GA/15가 과거·최근 모두 0이면 100, 최근만 0이면 120, 과거만 0이면 50입니다.

- 최근 10회와 이전 최대 20회는 GK 수행기록이 확인된 출전만 사용합니다. 일반 필드 출전은 GK 표본에 넣지 않습니다.
- 선방+실점=0이면 SAVE%=N/A입니다. 100% 선방률로 만들지 않습니다.
- 선방은 팀별 기록지 우선의 기존 `playerSaveRows` 연결 규칙을 사용합니다. 키퍼실점을 선방으로 읽거나 중복 합산하지 않습니다.
- 팀 실점과 키퍼 실점 합계가 불일치한 수행기록은 새 SLUMP 지표에서 제외합니다.
- 누락 지표는 재분배하되 모든 지표를 사용할 수 없으면 감소하지 않습니다.
- GK도 FORM·표본·지속·간격·시즌 한도 조건을 모두 적용하고 **DEF만** 감소합니다. 필드 MOM 보너스는 GK PI에 중복 적용하지 않습니다.

## 10. 시즌 한도·중복 방지·회복

### 한도

각 감소 이벤트에서 해당 연도 포지션 가중치를 정규화하여 `Σ(실제 축 감소×OVR 가중치)`를 계산합니다. 연간 1~12월 합계 최대 **1.5 OVR**입니다. 마지막 이벤트가 잔여 한도를 초과하면 축별 감소량을 같은 비율로 줄입니다. 능력치 최솟값도 지킵니다.

기존 결석·파울·SoccerBee·이전 LONG FORM 감소는 신규 SLUMP 한도에 합산하지 않습니다. 이후 성장률 구간이나 상한 효과 때문에 ON/OFF의 장기 BASE 차이는 이벤트 직접 영향 합계와 다를 수 있습니다. 한도는 **SLUMP 이벤트의 직접 영향**을 제한합니다.

### 중복 방지

고유 ID는 `[SLUMP-v1, 선수명, 경기일]`입니다. 원본 능력치에 감점 이벤트를 저장·덧붙이지 않고 매번 원본부터 날짜순으로 재생합니다. 한 재생 중 같은 ID를 다시 적용하지 않습니다. 새로고침이나 다른 화면 조회, Firebase 동기화가 추가 차감을 만들지 않습니다.

조회 기준일 이후 자료는 사용하지 않습니다. 과거 기록 정정이나 설정 변경은 해당 이력을 다시 계산합니다.

### 회복

종합 PI ≥85가 실제 출전 경기일 3R 연속이면 RECOVERED입니다. 그전에 감점 조건이 깨져도 추가 감소는 즉시 중단됩니다. 이미 감소한 능력치를 자동 가산하지 않습니다. 기존 성장 로직으로 이후 회복합니다. 회복 Story ON일 때만 `PERFORMANCE RECOVERY`를 표시합니다.

이전 V3.25.26 LONG FORM을 시작일 전에만 계산하므로 기존 BASE가 배포 시점에 갑자기 복원되거나 추가 감소하지 않습니다. 새 OFF는 신규 SLUMP만 중단합니다. 시작일을 과거로 변경하면 기존/신규 판정 경계도 바뀌므로 전체 이력이 재계산됩니다.

사용자가 수정한 기존 성장·SoccerBee·FORM·OVR 가중치를 유지합니다. 메뉴 공개 설정 및 JSON 백업·복원·Firebase 직렬화도 유지합니다. Firebase 보안 규칙이나 인증 방식은 변경하지 않았습니다.
